# ADR 0012 — Upgrade and harden the NoLift k3s cluster

**Status** Proposed · **Date** 2026-11-28

Upgrade to **k3s `v1.36.6+k3s1`** in two minor-version hops. Use the maintenance window for recovery checks and the cluster upgrade. Roll out mesh monitoring, pod security contexts, and dependency fixes independently so a problem in one change is easy to identify and reverse. Keep firewall changes out of this pass because the home server is also the development workstation. Security findings will go to Grafana and Loki only.

## 1. Protect administrator access and establish recovery

The live cluster has one home control plane and one private EC2 Spot worker. Both run `v1.34.5+k3s1`. Upstream Kubernetes 1.34 reached end of life on October 27. All 14 persistent volumes, both Cloudflare Tunnel replicas, the ingress data plane, and all four PostgreSQL instances are on the home node. Plan for a portal outage when that node restarts. UFW is already enabled on the home host, and the worker has no public IP or inbound AWS security-group rules. [Kubernetes release lifecycle](https://kubernetes.io/releases/)

- **Fix the cluster-admin kubeconfig first.** The home service explicitly starts with `--write-kubeconfig-mode 644`, and the file on disk is `0644`. Confirm the operator’s private administrative access works, change the persistent setting and file to `0600`, and verify the mode after restart. Review existing copies and who could read them. Changing file permissions cannot invalidate a previously copied certificate. [K3s cluster access](https://docs.k3s.io/cluster-access/)
- **Prove recovery before booking downtime.** The server journal identifies SQLite. Take a consistent off-host backup of the k3s datastore, server token, service configuration, and Rancher state. Back up PostgreSQL and the home-local application volumes separately. Rehearse restoration in isolation, including a database read, and measure the time it takes. Reserve that time at the end of the outage window. [K3s backup and restore](https://docs.k3s.io/datastore/backup-restore/) · [K3s rollback](https://docs.k3s.io/upgrades/roll-back)
- Record pre-upgrade health for storage provisioning, ingress, OIDC login, the test athlete’s sessions, and the protected IF service through its existing health path. Two known baseline issues matter here: k3s repeatedly reports an immutable `local-path` StorageClass mismatch, and the live export assertions already have known failures. Verify the active default StorageClass can provision a disposable claim before maintenance.

## 2. Upgrade through supported combinations

Rancher Manager sets the target. Its installed `2.13.3` release supports k3s through 1.34. Community-stable `2.14.3` supports 1.35, and `2.15.3` supports 1.36. Istio Ambient `1.32.0` supports both hops. [Rancher stable chart index](https://releases.rancher.com/server-charts/stable/index.yaml) · [Rancher 2.14.3 matrix](https://www.suse.com/suse-rancher/support-matrix/all-supported-versions/rancher-v2-14-3/) · [Rancher 2.15.3 matrix](https://www.suse.com/suse-rancher/support-matrix/all-supported-versions/rancher-v2-15-3/) · [Istio supported releases](https://istio.io/latest/docs/releases/supported-releases/)

| Stage | Planned change | Gate before continuing |
|---|---|---|
| Prepare | Use a supported `kubectl` for each hop. Upgrade cert-manager `1.20.0` to `1.21.3`, which supports Kubernetes 1.34–1.36. Through the existing network Terraform state, align Gateway API `1.2.0` and NGINX Gateway Fabric `2.6.3` to the documented `1.6.1` / `2.7.2` pair. Stage and verify that ingress change separately. | Certificate and admission webhooks respond. Existing HTTPRoutes are accepted, the waypoint is programmed, and public OIDC login works. |
| First hop | Upgrade Rancher `2.13.3 → 2.14.3`, then k3s `1.34.5 → v1.35.10+k3s1`. Upgrade the home server first. Reconcile the existing SSM worker bootstrap pin from the ready server, then upgrade the Spot agent. | Both nodes report the target version and are Ready. Verify DNS, cross-node traffic over Tailscale/Flannel, Istio, storage, and an authenticated portal read. |
| Second hop | Take a fresh recovery checkpoint. Upgrade Rancher `2.14.3 → 2.15.3`, then k3s `1.35.10 → v1.36.6+k3s1` in the same server–worker order. | Repeat the first-hop checks. Verify Argo sync, CNPG health, Dapr, workload identity, the deployment runner, the protected service, and the test athlete’s browser session. |

Pin versions in the deployment pipeline and preserve the existing k3s flags, OIDC issuer, and tailnet configuration. Keep an operator recovery path outside the in-cluster runner. Stop at the first failed gate. If a minor upgrade needs reversal, restore its matching binary and datastore checkpoint. A healthy 1.35 cluster is an acceptable stopping point for the first window. ## 3. Close the monitoring and pod-security gaps

- **Finish the existing mesh monitoring.** Both ztunnels are running, and Prometheus already receives waypoint HTTP metrics. The missing pieces are per-node TCP visibility and a working edge scrape. Ztunnel logs confirm STRICT mTLS rejects the current edge scrape. Add explicit ztunnel targets on `15020`, enroll the Prometheus workload in Ambient, and allow only its service-account identity to reach edge metrics on `9113`. Provision one Grafana dashboard for scrape health, waypoint requests/errors/latency, and ztunnel connections. Accept when both nodes report metrics, a normal portal request appears, the edge target is healthy, and existing scrape targets still work. [Istio Ambient observability](https://istio.io/latest/docs/ambient/usage/troubleshoot-ztunnel/)
- **Apply Restricted pod settings to portal workloads in small batches.** Start with version-pinned Restricted `warn` and `audit` labels on `powerlifting`. Canary `pl-rankings` with numeric non-root UID, `RuntimeDefault` seccomp, privilege escalation disabled, and all capabilities dropped. Verify it can write its `/data` `emptyDir` and use its projected AWS token. Expand through Argo-managed stateless services, checking image UIDs, writable paths, and injected containers. Enable namespace enforcement only after generated pods, jobs, Dapr, gateways, and stateful workloads pass admission and restart tests. Keep privileged infrastructure exceptions scoped to their owners. [Kubernetes Pod Security Standards](https://kubernetes.io/docs/concepts/security/pod-security-standards/)
- **Pilot Falco after the upgrade.** Self-hosted Falco is Apache-2.0 licensed and has no licence fee. Use its modern eBPF driver on the Spot worker first, with the worker’s toleration and container-scoped rules. Send selected JSON findings to Loki. The existing log collector only selects the portal and runner namespaces, and its Spot instance is unready, so verify collection with a harmless test event before claiming coverage. Expand to the home node only after checking resource use, noise, and that workstation command lines are excluded. [Falco licence](https://github.com/falcosecurity/falco/blob/master/COPYING) · [Falco Kubernetes deployment](https://falco.org/docs/setup/kubernetes/)

**Runtime decision.** Keep k3s-managed containerd and its current default runtime. gVisor and Kata can be selected through containerd per pod. gVisor is the lighter candidate for a future untrusted-code workload, but upstream has documented Ambient ingress failures, and current Falco removed its gVisor syscall engine. Kata needs virtualization support that most configured Spot instance families lack. Sysbox primarily serves nested Docker, Kubernetes, and systemd workloads. None warrants a production migration in this pass. [K3s containerd configuration](https://docs.k3s.io/advanced#configuring-containerd) · [Istio/gVisor compatibility report](https://github.com/istio/istio/issues/58573) · [Falco 0.44 release](https://github.com/falcosecurity/falco/releases/tag/0.44.0) · [AWS nested virtualization](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/amazon-ec2-nested-virtualization.html) · [Sysbox](https://github.com/nestybox/sysbox)

## 4. Reduce the 118 GitHub alerts

The default branch has **1 critical, 55 high, 45 medium, and 17 low** Dependabot alerts, with **23 open Dependabot PRs**. Axios accounts for 36 alerts and Multer for 22. All 27 checked Powerlifting ECR repositories already have scan-on-push enabled. Use those existing results before adding a scanner. [Repository security alerts](https://github.com/PierreStephaneVoltaire/ai-powerlifting/security/dependabot)

1. **Make the first three PRs verifiable.** The critical `proxy-addr` update (#34), Axios (#29), and Multer (#30) all have a sampled backend check that fails while loading AWS credentials, before the image builds. Give Dependabot a credential-free build and test path on GitHub-hosted runners. Keep authenticated image publishing in trusted CI. Verify the actual updates with `npm run build` from `src` and focused proxy, HTTP-client, and upload tests. [Failing CI job](https://github.com/PierreStephaneVoltaire/ai-powerlifting/actions/runs/45540010816/job/138956054555)
2. **Handle high-value findings without PRs.** Refresh `rustls` and `rustls-webpki` in the analytics, imports, and rankings lockfiles and run each crate’s locked tests. Four alerts concern npm `xlsx`, for which GitHub lists no patched version. The backend declares it, while the current import and export paths use separate services. Confirm there are no dynamic consumers, remove the dependency, and verify a workbook import/export round trip.
3. **Measure the result.** Take the compatible Go security updates through the assistant module’s tests. Re-query GitHub after default-branch updates, record the remaining critical/high alerts by package and owner, and defer major upgrades that require unrelated application changes. The first pass succeeds when the critical alert closes and each remaining runtime high has a fix or a documented disposition.

The main unverified risk is recovery time for the sole home server and its local data.
